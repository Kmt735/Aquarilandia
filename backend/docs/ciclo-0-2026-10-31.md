## 4. Incompatibilidades funcionais sem conflito textual

1. **Logs de falha sanitizados só no HTTP:** a sondagem com fixture confirmou `500` sem dado interno na resposta,
   mas o erro completo era copiado ao console. Pool e script tinham o mesmo padrão observado no código.
   Corrigido com [registrarErro](../src/utils/registrarErro.ts:1), usado pelo handler, pool e falhas inesperadas
   do criar-admin. Registra apenas mensagem fixa, contexto fechado e código no formato SQLSTATE; não copia
   message/stack/SQL/detail/parâmetros. O script informa só o ID no sucesso. Testes verificam os três caminhos,
   incluindo trigger real no banco durante execução do script.
2. **Documento de orçamento omitia Origin:** api.md dizia apenas público, embora o router combinado já
   exigisse Origin. Documentado como público **sem sessão**, com Origin=CORS_ORIGIN. HTTP confirma 201 com
   origem válida e 403 para ausente/null/incorreta, sem consultar sessão ou banco nessa rejeição.
3. **Relatórios e D-06 desatualizados:** a ausência histórica de rate limit/logout/script não vale para a
   versão combinada. Adendo de segurança e D-06 atualizados sem apagar o histórico. Login/logout/sessão,
   troca de senha e criação por script foram testados; não foram reimplementados.
4. **Rate limit depende do proxy em produção:** trust proxy=1 já existia. O teste comprova buckets por IP
   encaminhado e também que acesso direto com XFF forjado troca o bucket. Não se alterou topologia por
   suposição. Requer um proxy confiável que sobrescreva XFF e bloqueio do acesso direto ao backend.
5. **Frontend ainda usa mocks:** seus services não chamam a API; há proxy Vite /api, mas não há um fluxo real
   frontend→API para declarar homologado. Protocolo HTTP, CORS, Origin e cookies foram testados. Não se mudou
   frontend, IDs, DTOs, paginação ou preços para esconder essa limitação.
