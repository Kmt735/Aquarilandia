## 2. Contrato administrativo adotado

| Operação | Regra |
| --- | --- |
| `GET /api/produtos?incluir_inativos=true` | Sessão válida + papel atual admin; inclui ativos e inativos |
| `GET /api/produtos?incluir_inativos=true&ativo=false` | Somente inativos; `ativo=true` restringe aos ativos |
| `GET /api/produtos/:id?incluir_inativos=true` | Detalhe administrativo, ativo ou inativo; inexistente `404` |
| `POST /api/produtos/:id/reativar` | Sessão/admin/Origin; sem corpo ou `{}`; responde `200` |

A listagem conserva `{itens,total}`, filtros gerais/técnicos, padrão pagina=1/limite=20, máximo 100 e desempate por ID. Total considera todos os filtros, inclusive `ativo`, antes da paginação e no mesmo snapshot SQL. O filtro `ativo` só é admitido na listagem com `incluir_inativos=true`; não é um novo parâmetro público. Flags repetidas/arrays/valores diferentes dos booleanos literais são inválidos.

DTO administrativo: campos públicos existentes **mais `ativo:boolean`**. Detalhe acrescenta a mesma `ficha:{tipo,dados}|null`. Não inclui saldo bruto, timestamps, dados de sessão ou clientes. Exemplo reduzido de detalhe:

```json
{
  "id": 42, "categoriaId": 1, "categoria": "peixes", "nome": "Peixe de exemplo",
  "descricao": null, "marca": null, "preco": 4999, "imagemUrl": null,
  "emEstoque": false, "ativo": false,
  "ficha": { "tipo": "peixes", "dados": { "nomeCientifico": "Exemplo ilustrativo" } }
}
```

O exemplo reduz a ficha para mostrar a estrutura; respostas reais incluem todos os campos públicos definidos para a categoria.

**Autorização/cache:** GET/HEAD administrativos exigem os middlewares existentes `autenticar` e `exigirAdmin`, sem exigir Origin para leitura. Sem sessão válida: `401`; cliente autenticado: `403`. Papel reconsultado no PostgreSQL, incluindo revogação, expiração e conta inativa. Respostas administrativas e seus erros usam `Cache-Control:no-store`; GET/HEAD também `Vary:Cookie`. Reativação usa adicionalmente `exigirOrigem`, com a mesma origem fixa das escritas existentes.

**Reativação:** o PDF prevê o filtro de inativos, mas **não define uma rota de reativação**. `POST /api/produtos/:id/reativar` é extensão explícita adotada e documentada neste incremento, sujeita à revisão normal da equipe. Não foi interpretada como uma rota já aprovada no PDF.

| Situação | Resultado |
| --- | --- |
| Produto inativo existente | `200`, detalhe administrativo com `ativo:true` |
| Já ativo / operação repetida | `200`; nenhum novo UPDATE ou timestamp |
| Produto inexistente | `404` |
| ID/body/query inválidos | `400` |
| Sem sessão / cliente / Origin inválido | `401` / `403` / `403` |
| Falha inesperada no banco | `500` genérico, rollback quando aplicável |
| DELETE repetido | Continua `404`; sucesso inicial permanece `204` |
| PATCH comum com `ativo` | Continua `400`; PATCH em inativo permanece `404` |

A transação usa `comTransacao`, lock `FOR NO KEY UPDATE` por ID inclusive inativo e leitura do DTO na mesma conexão. A única edição de reativação é `ativo=true` e timestamp; preço, ID, categoria, ficha, imagem, estoque e histórico são preservados. Duas reativações têm sucesso com uma escrita no máximo. DELETE depois de reativar deixa inativo; reativar depois de DELETE deixa ativo. PATCH que observa inativo pode responder `404`; uma reativação posterior não reaplica esse PATCH. O estado pode mudar após a resposta por uma operação posterior.

Evidências: `backend/src/routes/catalogo.routes.ts:13`, `produto.controller.ts:103`, `produto.service.ts:31`, `produto.repository.ts:63`. Contrato completo e exemplos em `backend/api.md`; justificativas em D-44/D-45 de `backend/docs/decisoes.md`.

## 4. Carrinhos antigos e política de migração

Persistência encontrada: `localStorage`, chave **`aquarilandia-carrinho`**, anteriormente um array de linhas completas. Antes do Ciclo 1, IDs eram textuais e preço em reais; depois dele, IDs numéricos e `item.centavos=true`, ainda com snapshots completos.

```js
// Antigo, sem correspondência numérica confiável:
[{ id: 'betta-splendens', qtd: 1, item: { id: 'betta-splendens', preco: 20 } }]
// Snapshot do Ciclo 1:
[{ id: 42, qtd: 2, item: { id: 42, preco: 4999, centavos: true, emEstoque: true } }]
// Novo formato persistido:
{ versao: 2, itens: [{ id: 42, qtd: 2 }] }
```

`frontend/src/services/carrinho.js:6` valida e normaliza a leitura; `:40` serializa somente IDs/quantidades; `:42` reconstrói os itens pela API pública. `CartProvider.jsx:41` coordena a conferência e ignora respostas de requisições substituídas.

- Aceita somente IDs numéricos inteiros de 1 a 2147483647. IDs textuais, inclusive texto numérico, não são convertidos por adivinhação. Linha e item com IDs contraditórios são descartados.
- Ignora completamente preço, disponibilidade, nome, imagem e ficha salvos. ID real com metadados incompletos pode ser reconstruído pela API; não é preciso confiar no snapshot para isso.
- Agrupa IDs duplicados, preserva ordem e soma quantidades; quantidades precisam ser inteiros positivos. Ajusta o teto visual existente de 99 por produto, com aviso. Isso não representa saldo ou reserva.
- JSON sintaticamente inválido ou formato v2 incompleto é limpo com aviso. Estrutura/versão desconhecida é preservada, bloqueada para uso e exige limpeza explícita pelo usuário. Não sobrescreve automaticamente uma versão futura.
- Reescreve uma vez como versão 2. Recargas seguintes reconhecem esse formato e não repetem a migração. Os IDs válidos são preservados mesmo se a API estiver fora do ar.
- Produto `404` (inclusive inativo) ou `emEstoque:false` é removido com aviso. Falha de rede/5xx/contrato mantém ID/quantidade pendentes, sem snapshot utilizável. Retry reconstrói a linha e remove o aviso de falha quando resolvida.
- Consulta ao carregar, ao abrir/fechar o carrinho e ao retornar à aba. Adicionar e desfazer remoção também conferem a API; desfazer não ressuscita um produto desativado por causa de um snapshot antigo.
- Quantidade alterada durante requisição é preservada; removidos não reaparecem por uma resposta atrasada. Há no máximo quatro consultas simultâneas por conferência.
- Avisos aparecem por toast e na gaveta. Enquanto houver itens pendentes/conferência, resumo e cabeçalho mostram **“Aguardando conferência”/“Conferindo carrinho”**, sem apresentar uma soma parcial como total completo; continuar fica bloqueado. Na falha, há botão de nova tentativa.

Itens validados mantêm preço em centavos; apenas a apresentação e o seletor de total legado do protótipo usam reais. Não se usa mais preço antigo do armazenamento para compor o carrinho. O bloqueio no primeiro resumo do carrinho é proteção de apresentação, não implementação de checkout ou garantia comercial. Um navegador modificado pode manipular seu próprio estado: o futuro servidor de vendas deverá revalidar tudo.

- SQL usa parâmetros e fragmentos fechados; mapeamento de ficha é compartilhado. Reativação não aceita editar nenhum outro campo.
